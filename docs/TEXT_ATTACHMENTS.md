# Textual attachment ingestion

Text attachments selected through Zotero use the same private file registration, regular-file/reparse validation, immutable SHA-256 versions, current-scope guards and bounded Windows subprocess as PDF ingestion. The source kind remains `text_attachment`. The renderer sends scoped identifiers and parser limits, never paths, file bytes or a parser choice. The native resolver records the attachment MIME type in the snapshot, and the bridge checks it again before registration. Older text snapshots without this provenance require recapture (`SCOPE_STALE`); no filename or content-type guessing substitutes for it. Adding an absent MIME field does not change existing immutable content hashes.

Supported inputs:

- `text/plain`, `text/csv`, `text/tab-separated-values` and `text/markdown`: decoded original text, including line endings and Unicode, is retained without search normalization. CSV is a textual source here, not a table-import command.
- `text/html`: ordered HTML text nodes, with block boundaries and character references resolved. Head, script, style and template content are excluded. No scripts, styles, images or linked resources are executed/fetched.
- `text/xml` and `application/xhtml+xml`: strict XML parsing and ordered text nodes; XHTML excludes the same non-content elements. DTD/entity declarations are explicitly unsupported, including EPUB2/XHTML documents that depend on them.
- `application/epub+zip`: one declared rendition, a validated manifest and all XHTML spine units in reading order, including non-linear units. Each unit must contain extractable text; a missing/unsupported unit or image-only spine unit fails the document explicitly. Navigation/non-spine assets do not substitute for its reading order. Encrypted resources, unsupported compression and multiple renditions are explicit failures.

Encoding is strict UTF-8 by default. UTF-8/16/32 byte-order marks and supported declared encodings (Unicode variants, ASCII, ISO-8859-1 and Windows-1252) are recognized; decoding errors and binary controls fail. Unsupported `text/*` formats, including RTF, remain admitted source descriptors with an explicit `UNSUPPORTED_TEXT_FORMAT` ingestion failure. They never count as successful full-text coverage.

EPUB ZIP entries are read in memory from the verified inherited handle, never extracted to disk. Names, duplicates, encryption and symlink entries are checked. The archive is limited to 10,000 entries; total declared decompressed bytes and each bounded member read must fit the configured file-byte limit. The configured page limit also bounds EPUB spine units. Existing worker memory/time/output/cancellation limits apply. The unpaginated original-text unit is additionally bounded to `min(20,000,000, memory_bytes / 256)` Unicode characters to bound the engine's normalization map; exceeding it pauses with `TEXT_LIMIT`. Limits fail without publishing truncated content. Text reindexing rechecks the parser limits even when its immutable version is already cached.

Original file SHA-256 and byte count identify the original bytes; `evidra-text-file-v1` identifies the extraction policy. Text nodes and EPUB units are joined deterministically before search normalization and chunking. This is extracted original text, not a copy of the raw markup/ZIP file. As with existing PDF snapshots, the source file itself must still exist to inspect those raw bytes later.

Unpaginated text uses one internal storage unit, with no physical page number or label. Its evidence has `precision=text`, `page_index=null`, no rectangles, and offsets into that immutable text. Retrieval and full-scan planning consume the resulting document/chunks and preserve explicit ingestion failures in coverage. Empty plain/markup text is metadata-only; it is not classified as OCR success.

**Native navigation limitation:** the evidence panel verifies and displays literal excerpts, but has no verified location-opening operation for textual attachments. Zotero's EPUB Reader uses CFI positions, while the existing Evidra Reader-byte verification contract is PDF-specific. Reading the current native file again does not establish the bytes already loaded by a Reader. The panel labels this limitation and directs users to open the original attachment from Zotero; text files are never sent through PDF Reader/preview operations. Fixture ingestion is not native citation-navigation acceptance.

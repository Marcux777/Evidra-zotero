Native Reader observation on 10.0.1 (`.local/native-smoke/task2-native-reader-receipt.json`): `Zotero.Attachments.importFromFile({file,parentItemID,title,contentType})` imported the fixed synthetic PDF into the guarded profile. `Reader.open` selected the exact attachment; `getByTabID(win.Zotero_Tabs.selectedID)` and `reader._window` established ownership. The tab-specific `item-details` id is `reader.tabID + '-context'`. `getCustomPanes()` supplied the actual namespaced paneID; `pane.open=true`, context mode=item/collapsed=false and `scrollToPane(paneID,'instant')` rendered the visible 296x367 Evidra frame. `isPaneVisible`, exact item/tab ownership and null principal were checked. Reader close removed its context; main workspace reopened successfully. This does not yet prove evidence location/quote geometry.

Operational policy remains separate: ordinary Zotero operations use only the personal local helper, which lacks profile-selecting startup arguments. The user explicitly authorized the exact isolated-profile native test exception in NATIVE_VALIDATION_PLAN.md; that exception does not authorize personal-profile UI automation or library mutation.

## Test-profile isolation reference

The target [dataDirectory.js](https://raw.githubusercontent.com/zotero/zotero/10.0.1/chrome/content/zotero/xpcom/dataDirectory.js) handles an explicit `-datadir` before preference/default discovery (lines 55–78); it accepts an absolute path with an existing parent, or `profile`. A profile alone is insufficient isolation: the ordinary default-discovery branch inspects other profiles and the default data directory. The test launcher therefore must supply both an isolated profile and an explicit disposable data directory, then verify the running profile/data paths before any fixture write. This is a source-derived harness requirement, not evidence of an executed isolated launch. The [official multiple-profile guide](https://www.zotero.org/support/kb/multiple_profiles) also documents that automatic separate-data-directory behavior has not always occurred.

Two ancillary raw-source lookups for `defaults/preferences/prefs.js` and `app/assets/app.ini` returned tool Internal Error on 2026-09-05. They supplied no evidence; no startup or preference operation was attempted from them.

## Reading versus editing a group

`item.isEditable()` checks editing, including imported-file editing; it is not a read-permission API. A current group member can have `editable=false` and `filesEditable=false`. The source resolver must still support selected available content in that group, while future note writes require write permission. See [item.js](https://raw.githubusercontent.com/zotero/zotero/10.0.1/chrome/content/zotero/xpcom/data/item.js) and [groups.js](https://raw.githubusercontent.com/zotero/zotero/10.0.1/chrome/content/zotero/xpcom/data/groups.js).

The target sync runner marks a retained group `archived=true` when group access or membership disappears. Evidra's current-access requirement therefore treats an archived or missing library as unavailable, even when Zotero retains its local files. This is an implementation ruling inferred from [syncRunner.js](https://raw.githubusercontent.com/zotero/zotero/10.0.1/chrome/content/zotero/xpcom/sync/syncRunner.js), not a new remote permission check. The bridge observes Zotero's current local state; it cannot detect an unsynced remote membership change without Zotero reporting it. Revalidate known selected libraries/items on operations and revoke on relevant notifications; never call cloud APIs or scan unrelated libraries to discover changes.

The initial lookup of `xpcom/libraries.js` returned Internal Error; the verified registry is `xpcom/data/libraries.js`. The failed URL supplied no evidence and caused no Zotero operation.

## Measured Gecko transport and path behavior

The isolated native experiment at23:18Z confirms that a sandboxed content page cannot call its chrome parent's postMessage. A self-posted request can reach a privileged listener attached to that exact contentWindow: source is the child, origin is `null`, and isTrusted is true. The privileged reply arrives with source=null, empty origin and isTrusted=true. Receipt `.local/native-smoke/task2-native-transport-package-diagnostic-bounded.json` preserves both directions and the opaque principal. [MDN documents the null source for privileged postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage#using_window.postmessage_in_extensions); the empty origin is a measured target behavior, not a portable browser assumption. A native-ready signal must precede queued UI requests, and synthetic/unexpected senders must be rejected.

The same experiment found `PathUtils.join(system, 'WindowsPowerShell\\v1.0\\powershell.exe')` throws OperationError/NS_ERROR_FILE_UNRECOGNIZED_PATH. Pass each fixed path component separately. Preserve OperationError/UnknownError and the numeric DOMException result in structural diagnostics; [Mozilla documents the IOUtils exception categories](https://firefox-source-docs.mozilla.org/dom/ioutils_migration.html#errors-are-reported-as-domexceptions). Raw native messages may contain paths and are not suitable for public error payloads.

Installed `omni.ja/modules/subprocess/subprocess_common.sys.mjs:495-526` confirms readString without a length returns an empty string at EOF and decodes successive chunks in streaming mode. This matches the adapter's pipe-drain contract; supplying an exact length has different EOF rejection behavior.

The actual production iframe delivers its child document load through capture phase, with the document as event target. Initialize only after a trusted event for the exact owned contentDocument, fixed expected UI URI and complete readiness; ignore early resource/foreign-document loads without consuming the listener. Native receipt `task2-native-load-diagnostic.json` establishes the target behavior, corroborated by [Mozilla's chrome iframe discussion](https://bugzilla.mozilla.org/show_bug.cgi?id=1657182#c5).

The UI's `sandbox="allow-scripts"` also blocks native form submission before the submit event is fired. The [HTML submission algorithm](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#form-submission-algorithm) returns on the sandboxed-forms flag at step4, before event dispatch at step5.6. Actual receipt `task2-native-trusted-form-diagnostic.json` proves trusted input, React state update and an enabled trusted click, followed by no submit or bridge request. UI commands therefore use explicit type=button actions and appropriate single-line Enter handling, with IME/busy checks. A form element may provide semantics and styling; its submit event cannot be the command path. Keep the existing sandbox and CSP unchanged.

The earlier test helper's synthetic input event did not reach the content's normal event path. For authorized test-profile input only, Mozilla's [nsITextInputProcessor interface](https://searchfox.org/mozilla-central/source/dom/interfaces/base/nsITextInputProcessor.idl) and [Input.insertText implementation discussion](https://bugzilla.mozilla.org/show_bug.cgi?id=1595177#c6) define beginInputTransactionForTests/commitCompositionWith. Root verified the exact child document and focused input before using it; the actual receipt records trusted capture/bubble events and matching input value/React attribute. This is test instrumentation, not a production bridge capability.

The same opaque content realm reports isSecureContext=false and crypto.randomUUID=undefined, while getRandomValues is available and returns the requested32bytes. Privileged Xray inspection of that same window misleadingly reports randomUUID as a function. The fixed content-script experiment `task2-native-crypto-diagnostic.json` records the actual TypeError and both observations. [Gecko ESR140 Crypto.webidl](https://raw.githubusercontent.com/mozilla/gecko-dev/esr140/dom/webidl/Crypto.webidl) marks randomUUID as SecureContext and does not mark getRandomValues. Production UI keys therefore use getRandomValues directly, with no conditional provider or algorithm fallback.

The actual authorized multiwindow experiment `task2-native-multiwindow-receipt.json` verifies `Zotero.openMainWindow()` plus identification through the new member of `Zotero.getMainWindows()`, exact document URI `chrome://zotero/content/zoteroPane.xhtml` and ready collectionsView. Acquire each window's fresh Tools command and iframe from its own document. Closing the second native window preserves the first workspace; normal final-window close removes the owned engine. Native keyboard testing uses the focus-verified frame's TextInputProcessor keydown/keyup pair; always keyup in finally.

Within the isolated profile, `Zotero.Prefs.set('browser.theme.toolbar-theme',1,true)` propagated light mode and value0 dark mode to both actual frame media queries and CSS colors. Preserve/restore the user's prior preference presence, not only its numeric value. Setting the exact owned iframe's `docShell.browsingContext.fullZoom=2` produced450x264logical viewport and the responsive single-column layout, with no horizontal overflow; reset to its original value. These are measured target APIs for authorized tests, not newly exposed product bridge operations.
